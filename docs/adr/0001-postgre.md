Utiliser PostgreSQL 17 comme système de gestion de base de donnéesStatut : acceptéeDate : 2026-11-10Décideurs : l'équipe Data & TechContexteDans le cadre du Challenge Sales de Givaudan, notre rôle côté Data est de structurer et d'exploiter efficacement les données de ventes, les catalogues de produits/ingrédients, les profils clients et les retours d'intelligence artificielle. Le projet est soumis à une contrainte de temps stricte (un prototype complet à livrer en deux semaines), doit tourner de manière identique sur toutes les machines via Docker, et s'intègre dans un écosystème de développement en Python 3.13. Nous avons besoin d'un stockage capable de lier des données relationnelles strictes (commandes, clients) et des structures semi-structurées (payloads d'IA, métadonnées de vente).   OptionsPostgreSQL 17 : Le standard de l'open source relationnel. Il offre une gestion native et ultra-performante du type JSONB (idéal pour stocker les prompts et réponses d'IA de la brique sales), de puissantes capacités analytiques pour croiser les données de vente, une image Docker officielle stable et une excellente intégration avec l'écosystème Python (SQLAlchemy, Psycopg3).   SQLite : Solution ultra-légère sans serveur. Ses limites d'accès concurrents (entre l'API FastAPI et les scripts d'exploration de données) et l'absence de fonctions analytiques avancées la rendent inadaptée à un projet orienté data and sales.MongoDB : Base NoSQL très souple pour du document JSON, mais elle complexifie l'écriture de requêtes analytiques croisées et offre moins de garanties relationnelles pour structurer proprement un pipeline de vente.DécisionNous choisissons PostgreSQL 17 parce qu'en tant qu'experts Data, c'est le choix le plus polyvalent : il garantit l'intégrité de nos modèles relationnels tout en absorbant avec fluidité les données semi-structurées de l'IA grâce au JSONB, le tout s'intégrant parfaitement dans notre stack conteneurisée.   ConséquencesPositives : Puissance des requêtes SQL et analytiques pour le volet Sales, manipulation transparente du JSON, et outillage data extrêmement riche.Négatives, à accepter : La nécessité de gérer un conteneur de base de données dédié dans notre stack Docker.   À revoir si : Le projet pivote vers une architecture Big Data distribuée nécessitant un Data Warehouse Cloud natif.
